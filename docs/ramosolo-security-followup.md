## Existing controls and review coverage

- Public pages, booking requests and guest proposal responses use dedicated public handlers. Booking writes and guest decisions are POSTs. Guest details require the opaque link, separate code, current consent and a still-unlinked patient. The synthetic delivery sink only runs in tests.
- The medical dashboard, patients, appointments, calendar, admissions, continuity, records, permissions, referrals, consent, reviews, action queues and both CSV exports were traced through their role, active institution and patient checks. Staff use assignments and resource-specific grants. Patient accounts receive their own booking records and explicitly shared care information. The education placeholder remains separate. CSV exports use fixed attachment names and escape spreadsheet formula cells.
- Institution switching, administration and account-security handlers use membership or current session checks. The session JSON returns authentication status, deadlines and a page identifier. Revocation uses server-side session rows, account versions and membership stamps. Staff MFA is mandatory outside synthetic tests. OIDC ties its short-lived exchange to the browser and requires a CSRF-protected confirmation POST. Password recovery is an identity-proofed CLI workflow with independent approval. There is no anonymous password reset handler.
- State-changing forms use global Flask-WTF CSRF protection. Read audit entries and the transient OIDC callback exchange do not edit bookings, medical records or memberships. Queries use SQLAlchemy bound values. The interpolated transaction search path uses a validated identifier, and local schema repair commands use fixed identifiers. Jinja autoescaping and generic error responses prevent raw field or exception rendering. The global no-store policy covers sensitive pages, JSON, redirects, downloads and errors.
- The public static inventory is `css/style.css` and `js/session-warning.js`. The file handler rejects links and junctions, including a linked static root. The tests cover private-file, source, backup, upload and debug paths through Flask. App cookies use HttpOnly and SameSite=Lax, with Secure in production. HSTS, CSP and host validation run at the Flask boundary. A separate edge file server, cache or debugger can bypass application protections and must be checked on the real deployment.
- The read-only hosted catalog check found no direct views depending on Ramosolo relations and no literal `ramosolo` references in routine source or routine configuration within `public` and `graphql_public`. Those checks do not resolve indirect or dynamic references or reveal the hosted Data API exposure list.
- The secret scan is pattern-based. It does not open protected data files, excluded historical objects or arbitrary binary payloads. The historical Supabase CLI `pooler-url` was identified by path alone, so no additional credential is attributed to that file.

## Verification results

- `python -m pytest -q` completed with 311 passed, one skipped and three existing expected failures. The run used in-memory SQLite and an isolated PostgreSQL 18 cluster with synthetic records. The live-shaped replay exercised the permission drafts, restricted-role login and session revocation, booking concurrency and reminder eligibility. A fresh local PostgreSQL 17 replay was unavailable because the installed binaries were incomplete.
- Synthetic Chromium checks passed for anonymous and medical role views. HTML, CSS, JavaScript, session JSON, denied responses and browser storage excluded the secret and cross-scope canaries. The browser made no external page requests. A separate desktop and mobile check passed staff MFA, idle expiry, and fresh authentication before record reload.
- The redacted scan covered 33 commits and 534 source blobs. It reported no pattern matches in eligible current or staged files. The historical database URL and the excluded cache in the handoff were reported by path. The checked-in migration 010 still has the reviewed SHA-256 hash, and `git diff --check` passed.

## Operator configuration and deployment decisions

1. Identify the actual hosting topology and deployed dependency versions. The checkout provides a Waitress entry point and example command. The live proxy configuration, edge cache rules and production origin were unavailable in this review. Use `APP_ENV=production`, `FLASK_DEBUG=0`, exact `APP_TRUSTED_HOSTS`, the canonical `AUTH_PUBLIC_URL`, and PostgreSQL TLS with `sslmode=verify-full` and the provider CA. Inject the database URL, signing and MFA keys, and any Gmail, SMS and OIDC credentials into the applicable process through the protected secret store. Keep the migration and mail credentials out of the web process. Set `PUBLIC_INSTITUTION_ID` when the portal serves more than one medical institution. Preserve the existing provider enablement and consent gates.
2. For one same-host TLS edge proxy, preserve the request `Host` and overwrite `X-Forwarded-Proto` and `X-Forwarded-For` with the scheme and client address determined at that edge. Block direct access to the Waitress listener, strip unneeded forwarding headers and set `APP_TRUSTED_PROXY_HOPS=0` when Waitress handles forwarding. Substitute the actual trusted peer and count for other topologies. A shared proxy address would make anonymous users share an authentication budget. [Waitress proxy settings](https://docs.pylonsproject.org/projects/waitress/en/stable/arguments.html)

   ```powershell
   waitress-serve --listen=127.0.0.1:8000 --trusted-proxy=127.0.0.1 --trusted-proxy-count=1 --trusted-proxy-headers="x-forwarded-for x-forwarded-proto" --call wsgi:create_production_app
   ```

3. Confirm redirects, host filtering, secure cookies, HSTS, CSP, cache headers and private-path denials through real HTTPS on staging. Configure the edge to honor no-store, avoid repository/static aliases, and redact full paths containing opaque links, queries, headers and request bodies from retained logs. Run `python verification/check_release_secrets.py --history --artifact <release-path>` against the release candidate. An artifact finding fails the command even when working-tree scans are clean.
4. Run `supabase/review/reconciliation_constraints_preflight.sql` as the migration principal with `psql -X --set=ON_ERROR_STOP=1` before rehearsing migration 010. Treat a changed fingerprint as a stop condition and review the catalog differences. Rehearse the immutable reviewed chain through 017, then `verification/runtime_roles.sql` and `supabase/review/runtime_permissions_followup.sql`, against an isolated live-shaped fixture matching the hosted PostgreSQL version. The limiter uses `delivery_limits` from the existing delivery migration. Provision distinct protected logins for the web and delivery service after approval, and schedule `purge-expired-auth` through a separately authorized maintenance connection. The SQL drafts leave the proposed roles `NOLOGIN` and contain no passwords. Keep DDL and assisted recovery with the authorized owner workflow. Rehearse rollback to the previous approved application and connection while preserving histories and queued work.
5. Run `supabase/review/security_runtime_readonly.sql` through the protected deployed Flask connection to identify both database principal and effective role. The previous reconciliation runbook recorded `postgres` with `BYPASSRLS` through that connection. The current management connector check verified catalog grants only. Review hosted Data API exposed and extra search-path schemas, Realtime publications, API grants, public views/routines that might reference private relations, and object-creator defaults. The tracked Supabase CLI configuration exposes `public` and `graphql_public`. Keep `ramosolo` private. If approved after checking for other consumers, disable the hosted Data API. For future private routines, revoke `PUBLIC` execution when creating each routine and grant only the callers that need it. Review global default changes separately because they can affect other schemas. [Supabase Data API security](https://supabase.com/docs/guides/api/securing-your-api)
6. Treat current role policies as database service boundaries. Flask-Login accounts do not supply a Supabase Auth JWT to PostgreSQL. The runtime role must support all permitted Flask workflows, so it can see rows across institutions on objects it needs. Database-enforced tenant isolation would require a separate design for trusted request identity and institution context per transaction, including guest, worker and pooler paths. Confirm that the runtime cannot inherit the migration owner or be assumed by a Data API role.
